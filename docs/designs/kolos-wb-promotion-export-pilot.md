# Пилот Колоса на выгрузках акций WB

Статус — черновик на утверждение. GStack Office Hours, Builder mode. Ветка `master`, 27 ноября 2026 года.

## Цель

Владелец Колоса хочет один раз объяснить Codex новое правило проверки выгрузок, а затем получать правильный результат на новых данных без участия модели. Первый тест на Windows проверяет сохранение и перенос урока. Второй результат теста — сравнение фактических токенов за всю серию с прямым использованием Codex.

## Решение

- Выбран локальный пилот в текущем репозитории. Его входы — тестовые манифесты с обезличенными идентификаторами. Этот тест станет проверкой для будущего установочного пакета. Вариант с установкой плагина до проверки обучения отложен.
- Учебная задача меняет количество свежих выгрузок, нужных для полноты. В исходной версии нужна одна выгрузка на ожидаемую акцию. В учебной версии нужны две. Версия правила задана явно. В тестовом наборе записи свежих выгрузок представляют разные файлы.
- При первом корректном манифесте с неизвестной версией Колос один раз запускает Codex с короткой инструкцией о новом правиле. Codex возвращает декларативное условие в заданной схеме. Исполнитель принимает только допустимую операцию с типизированным порогом. Текущая проверка полноты и лабораторная грамматика уже поддерживают сравнение числа выгрузок с порогом.
- Колос проверяет кандидата локально по заранее зафиксированным эталонным результатам, которые закрыты от Codex на этапе урока. После проверки он сохраняет отдельный снимок памяти и правило под новой версией. В следующем процессе проверка читается из этого снимка. Тест без снимка, с отключённым вызовом агента, должен вернуть запрос на урок. Ошибочный кандидат, повреждённый снимок и незавершённое сохранение оставляют прежнюю рабочую версию доступной.
- Полнота в учебной версии определяется по числу свежих выгрузок. Две засчитываются, одна и ноль означают недостачу, три — излишек. Две штатные выгрузки не поднимают сигнал о дубле по правилу исходной версии. Тестовый результат сохраняет диагностику просроченных и неудачных выгрузок. Исходная версия сохраняет прежнюю классификацию.

## Приёмка

| Этап | Вход | Что подтверждаем |
|---|---|---|
| 1. Исходная версия | Первый манифест | Колос даёт эталонный ответ без Codex. |
| 2. Урок | Первый манифест учебной версии и короткая инструкция | Ровно один запуск Codex. Колос принимает прошедшее локальные проверки правило, сохраняет его и получает правильный результат по манифесту. |
| 3. Повтор | Другой манифест учебной версии со свежими идентификаторами акций и с 0, 1, 2 и 3 выгрузками | Новый процесс загружает сохранённое правило. Адаптер Codex отключён. Правильный результат при нуле вызовов модели и новом идентификаторе запуска. |
| 4. Регрессия | Другой манифест исходной версии | Старое правило по-прежнему даёт правильный результат без Codex. |

Отдельные проверки подтверждают зависимость от урока и отказ при ошибочном кандидате. Повтор с отключённым адаптером и отсутствующим снимком должен показать, что урок требуется. Кандидат, у которого правильный ответ на учебном манифесте и неверный на контрольном примере, должен быть отклонён. Если фактический урок не прошёл проверку или Codex завершился ошибкой, фиксируем расход попытки и завершаем измеряемую серию с ошибкой. Контроль с намеренно неверным кандидатом выполняется локально.

## Замер токенов

Контрольный вариант — Codex напрямую проверяет те же четыре манифеста по тем же условиям. Для обоих вариантов фиксируем модель и доступные входные данные. Для прямого Codex каждый манифест проверяется в новой сессии. Отдельная локальная проверка сверяет результаты обеих веток с одной эталонной разметкой.

В отчёте на каждый манифест записываем версию правила, итог проверки, число запусков Codex, входные, выходные и кэшированные токены из `usage`. Кэшированный вход входит в общий вход. Для этапов с подтверждённым отсутствием вызова записываем ноль. Если модель вызывалась, но `usage` отсутствует, показываем неизвестный расход. Бюджет урока считается по одному запуску Codex CLI, а токены учитываются целиком за этот запуск.

Суммируем расход основного цикла по каждому варианту и показываем разницу. Цена урока и любые модельные вызовы проверки входят в итог Колоса. Менее дорогой результат считается экономией только при подтверждённой правильности обеих веток и полном учёте токенов. Само сравнение публикуется независимо от знака разницы.

## Доставка и следующий этап

Результат первого этапа — локально воспроизводимая проверка из текущего репозитория и отчёт по запускам. После успешной приёмки этот же сценарий войдёт в проверку установочного архива Windows и плагина Codex. Публичный релиз и сборка для распространения относятся к следующему этапу.

На инженерном ревью нужно закрепить формат версии и снимка, подготовить четыре манифеста с эталонными результатами и определить, как отчёт подтвердит, что повторный процесс использовал сохранённый урок.
