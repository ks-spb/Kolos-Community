# Пилот Колоса на выгрузках акций WB

Статус — утверждён 27 ноября 2026 года. GStack Office Hours, Builder mode. Реализация от `main` в Kolos-Community. [План и результат пилота](../plans/kolos-wb-promotion-export-pilot.md)

## Цель

Владелец Колоса хочет один раз объяснить Codex новое правило проверки выгрузок, а затем получать правильный результат на новых данных без участия модели. Первый тест на Windows проверяет сохранение и перенос урока. Второй результат теста — сравнение фактических токенов за всю серию с прямым использованием Codex.

## Решение

- Выбран локальный пилот в текущем репозитории. Его входы — тестовые манифесты с обезличенными идентификаторами. Пилот использует отдельный вход запуска и чистый каталог с собственной копией исходного снимка. Штатные профили WB и Ozon продолжают читать свои снимки. Этот тест станет проверкой для будущего установочного пакета. Вариант с установкой плагина до проверки обучения отложен.
- Учебная задача меняет количество свежих выгрузок, нужных для полноты. В исходной версии нужна одна выгрузка на ожидаемую акцию. В учебной версии нужны две. Версия правила задана явно. В тестовом наборе записи свежих выгрузок представляют разные файлы.
- При первом корректном манифесте с неизвестной версией Колос один раз запускает Codex с короткой инструкцией о новом правиле. Codex возвращает декларативное условие в заданной схеме. Исполнитель принимает только допустимую операцию с типизированным порогом. Текущая проверка полноты и лабораторная грамматика уже поддерживают сравнение числа выгрузок с порогом.
- Колос проверяет кандидата локально по заранее зафиксированным эталонным результатам. Учебная сессия получает текущий манифест, короткую инструкцию и схему ответа. Контрольные входы и эталонные ответы доступны только локальной проверке. После проверки Колос сохраняет отдельный снимок и правило под новой версией. Отчёт о повторном запуске фиксирует отпечатки фактически загруженных правила и снимка. Они должны совпасть с отпечатками, сохранёнными после урока.
- Полнота в учебной версии определяется по числу свежих выгрузок на ожидаемую акцию. 0 и 1 означают недостачу, 2 означают полноту, 3 и более означают излишек. В учебной версии список избыточных выгрузок строится только по свежим строкам. Для двух свежих и дополнительной просроченной или неудачной попытки полнота сохраняется, а дополнительная попытка попадает только в свой диагностический список. Исходная версия сохраняет прежнюю классификацию. В манифестах зафиксированы ожидаемые ID акций и момент проверки по Москве. Обе ветки используют этот момент для определения свежести.

## Приёмка

| Этап | Вход | Что подтверждаем |
|---|---|---|
| 1. Исходная версия | Первый манифест | Колос даёт эталонный ответ без Codex. |
| 2. Урок | Первый манифест учебной версии и короткая инструкция | Ровно один запуск Codex. Колос принимает прошедшее локальные проверки правило, сохраняет его и получает правильный результат по манифесту. |
| 3. Повтор | Другой манифест учебной версии. Новые ID, 0, 1, 2 и 3 свежих выгрузки, включая ожидаемую акцию без записей и две свежие с дополнительной неудачной или просроченной попыткой | Новый процесс загружает сохранённое правило. Адаптер Codex отключён. Правильный результат при нуле вызовов модели и новом идентификаторе запуска. |
| 4. Регрессия | Другой манифест исходной версии | Старое правило по-прежнему даёт правильный результат без Codex. |

Локальные проверки включают отсутствие снимка при отключённом адаптере, намеренно неверный кандидат, повреждение снимка и незавершённое сохранение. Отсутствие снимка возвращает запрос на урок. Неверный кандидат проходит проверку схемы и даёт правильный ответ на учебном манифесте, но отклоняется на контрольном примере. Повреждённая или незавершённая запись оставляет новую версию недоступной и позволяет выполнить исходную. Отдельный тест с другим допустимым порогом подтверждает чтение порога из сохранённого правила. Эти проверки выполняются локально. Если фактический урок не прошёл проверку или Codex завершился ошибкой, фиксируем расход попытки и завершаем измеряемую серию с ошибкой.

## Замер токенов

Контрольный вариант — Codex напрямую проверяет те же четыре манифеста по тем же условиям. Для обеих веток фиксируем модель и конфигурацию Codex. Каждый вызов идёт в свежей сессии с доступом только к текущим входным данным. В контрольном варианте Codex запускается один раз на манифест. Локальная проверка сверяет результаты обеих веток с единой разметкой в одинаковой схеме. Сравниваем полноту по ID и отдельные списки просроченных, неудачных и неожиданных выгрузок. Для исходной версии также сверяем повторы, для учебной — излишек свежих выгрузок.

В отчёте на каждый манифест записываем версию правила, итог проверки, число запусков Codex, входные, выходные и кэшированные токены из `usage`. Кэшированный вход входит в общий вход. Сохраняем доступный `usage` и при неуспешном ответе. Для этапов с подтверждённым отсутствием вызова записываем ноль. При неполном `usage` показываем известную часть, а общий расход и разницу отмечаем как неизвестные. Бюджет урока считается по одному запуску Codex CLI, а токены учитываются целиком за этот запуск.

Суммируем расход основного цикла по каждому варианту и показываем разницу. Цена урока и любые модельные вызовы проверки входят в итог Колоса. Менее дорогой результат считается экономией только при подтверждённой правильности обеих веток и полном учёте токенов. Само сравнение публикуется независимо от знака разницы.

## Доставка и следующий этап

Результат первого этапа — локально воспроизводимая проверка из текущего репозитория и отчёт по запускам. После успешной приёмки этот же сценарий войдёт в проверку установочного архива Windows и плагина Codex. Публичный релиз и сборка для распространения относятся к следующему этапу.

На инженерном ревью нужно закрепить формат версии, снимка и квитанции запуска, а также спланировать четыре манифеста с эталонными результатами.
