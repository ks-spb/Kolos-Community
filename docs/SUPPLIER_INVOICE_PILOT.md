# Колос в сверке счета поставщика

Пилот запускает локальную сверку в режиме чтения. На входе структурированные поля счета и снимок заказов из штатного чтения 1С. Колос применяет выученную последовательность к ИНН поставщика, ИНН покупателя и валюте. Исполнитель пересчитывает суммы и НДС и сопоставляет строки по точному артикулу или по подтверждённой связке с конкретной карточкой 1С.

## Вход и результат

Команда `python -B -m kolos_states.supplier_invoice teach` обучается на JSON из stdin. Команда `python -B -m kolos_states.supplier_invoice read --memory <путь к memory.json>` повторяет сверку на новых данных. У обеих команд есть параметр `--output-root` для рабочей папки отчётов. Используйте UTF-8. Каждый запуск получает свой `run_id` и сохраняет `handoff.json`.

- `invoice` содержит `number`, `date`, `supplier_inn`, `buyer_inn`, `currency`, `tax_mode` (`added` или `included`), `subtotal`, `vat`, `total`, `delivery` и `lines`. Строки содержат `article`, `unit`, `quantity`, `price`, `amount`, `vat_rate` и характеристику `variant`, если она есть. `delivery` равна `null`, если в материалах нет суммы, или содержит `amount`, `vat` и явный признак `included`. Денежные значения и количества передаются десятичными строками.
- `orders` перечисляет снимки заказов с полями `number`, `state`, `supplier_inn`, `buyer_inn`, `currency`, `total`, `price_includes_vat` и `lines`. Строка заказа содержит `code`, полное `name`, подтверждённый `supplier_article` или `null`, `unit`, `variant`, `quantity`, `amount` и `vat`.
- `confirmed_links` содержит только однозначные подтверждения для данного документа. Каждая запись задаёт `number`, `date`, `supplier_inn`, `buyer_inn`, `currency`, `article`, `unit`, `code`, `variant` и ссылку на основание `evidence`.

`reconciled` означает, что заказ найден однозначно и его строки сопоставлены. Отчёт сохраняет расхождения. `needs_review` показывает кандидатов и неустановленные артикулы. `blocked` означает ошибку данных или отсутствие проверенной памяти. При любом результате `may_write` равно `false`. ChatGPT сверяет факты с исходным документом и продолжает существующий навык с его условиями подтверждения.

Для первого опыта используются исторические данные до исправления заказа, подтверждения из исходного чата и отдельная копия заказа после исправления. Входные материалы, память и отчёты хранятся в локальной папке `tests/desktop-output/supplier-invoice`. Память сохраняет роли и последовательность, ИНН остаются во входных материалах. Платёжные реквизиты для этого шага не нужны.

## Вызов из рабочего навыка

После разбора счёта и чтения заказов по штатному OData подготовь только поля из раздела «Вход и результат». Передай полный набор прочитанных открытых заказов нужной организации и поставщика. Сохрани характеристики и единицы, подтверждённые справочником. Денежные значения передавай десятичными строками с точкой. Заполняй `supplier_article` только из подтверждённой связи с поставщиком. Связку `confirmed_links` принимай только для точного счёта с проверенным основанием. Предыдущий пример сам по себе такого подтверждения не даёт.

- Добавь `snapshot` с `kind: "1c_odata"`, `observed_at` в ISO 8601 с часовым поясом и `complete: true` только после проверки полноты выборки. Для исторической проверки используй `kind: "historical"`. Контрольные поля снимка нужны локальному адаптеру.
- Запусти из корня репозитория Колоса команду `python -B -m kolos_states.supplier_invoice_skill run --output-root <папка проекта навыка>/outputs/kolos-supplier-invoice`. Передай UTF-8 JSON через stdin. При сборке входа используй короткую проекцию из локального источника. Значения реквизитов и содержание счёта в журнал запуска не выводи. У каждого запуска свой `run_id` из латинских букв, цифр, подчёркиваний и дефисов.
- Если счёт нечитаем, источник недоступен либо случай не поддержан, передай только `run_id` и `skip_reason` со значением `invoice_unreadable`, `snapshot_unavailable`, `snapshot_incomplete` или `unsupported_case`. При ошибке запуска или отсутствии `receipt.json` явно укажи, что результат Колоса не получен. Штатный сценарий навыка применяй по его правилам.
- Сверь ID и поля локальной квитанции `<output-root>/<run_id>/receipt.json` с ответом команды. В ответе команды присутствует её `receipt_sha256`. Если квитанция содержит `handoff`, прочитай по нему отдельный отчёт сверки. Команда `review` проверит его контрольную сумму. `transmitted_fields` показывает имена и количество фактически поданных полей, `filtered_counts` показывает число удалённых полей по разделам, `missing_fields` показывает пустоты схемы. Метаданные получателя, памяти, времени и выполненных шагов хранятся в той же квитанции. Отсутствие доставки в счёте не подтверждает, что её стоимость снаружи равна нулю.
- Самостоятельно сверь счёт и исходный снимок. Перед рабочей записью перечитай текущий заказ по его точной ссылке и проверь состояние и записанный состав. При неоднозначном или старом снимке штатная сверка продолжается с текущими подтверждёнными сведениями. Вердикт Колоса не заменяет подтверждения по документам, которые требуются навыком.
- Выполни той же командой `review` вместо `run`. Передай `run_id`, исходный `receipt_sha256`, `verdict`, `checks` и `findings`. Вердикт `confirmed` означает проверенную сверку, `correct_stop` означает подтверждённую остановку, `discrepancy` означает выявленную ошибку, `not_verified` означает отсутствие независимых доказательств. `checks` может включать `invoice_source`, `order_source`, `live_order_readback`, `article_confirmation`. Для подтверждения живого результата требуется чтение текущего заказа. При расхождении укажи коды `invoice_values`, `snapshot_coverage`, `order_selection`, `line_mapping`, `arithmetic` или `other` в `findings`. В других случаях `findings` пуст.

В блоке «Работа Колоса» кратко покажи, какие группы данных переданы и пропущены, результат Колоса и независимый вердикт, что улучшить по этому случаю и какие чтения или расчёты можно кандидатами отдать ему следующим шагом. Ссылайся на `receipt.json` и `review.json`. Храни этот блок вместе с итогом счёта. Если следующим сообщением владелец подтверждает ранее подготовленные действия, повторно не обрабатывай уже проверенный счёт ради отчёта.

## Связанные оплаты и возможные дубли

После однозначного выбора заказа запусти `payments` вместо `run` с тем же `--output-root` и собственным `run_id`. Используй чтение 1С, предусмотренное контрактом навыка. Перед записью заказа и перед подготовкой поручения используй снимок на соответствующем этапе. Если между этапами данные менялись, перечитай их. Для режима «только проверка» достаточно одного актуального снимка. Штатную проверку поступлений сохрани.

- Снимок охватывает `Document_ПлатежноеПоручение`, `Document_РасходСоСчета` и `Document_РасходДСПлан`. Прочитай все страницы в границах поставщика, организации, заказа и периода проверки с учётом ссылок в строках, входящего номера счёта, назначения и суммы. Используй период и фильтры штатной проверки навыка. Сохрани в исходных материалах границы и время чтения. `snapshot.complete` ставь в `true` после проверки полноты всех трёх выборок. При недоступной сущности, неясной валюте или пропущенной части передай `skip_reason` (`snapshot_unavailable`, `snapshot_incomplete`, `unsupported_case`) и объясни остановку.
- В `scope` передай GUID `order_ref`, `supplier_ref`, `buyer_ref`, `currency_ref`, номер и дату счёта `invoice_number`, `invoice_date` (`YYYY-MM-DD`). `proposed_amount` — согласованная сумма именно текущего действия в валюте документа, десятичной строкой. Если она неизвестна, передай `null`.
- В `documents` передай массивы `payment_orders`, `bank_expenses`, `expense_requests`, в том числе пустые. Для каждого документа положи `Ref_Key` в `ref`, `Number` в `number`, ссылки контрагента, организации и валюты в `supplier_ref`, `buyer_ref`, `currency_ref`. Валюту бери по реально используемому реквизиту сущности. В `order_refs` собери ссылки на «Заказ поставщику» из шапки и строк `РасшифровкаПлатежа`, в том числе `Заказ_Key`, пары `Заказ` / `Заказ_Type` и `ДокументОснование` / `ДокументОснование_Type`. Используй только подтверждённый тип ссылки. `invoice_number` и `invoice_date` заполняй из реквизитов этого документа, при отсутствии передай `null`. `invoice_hint` равен `true`, если в назначении явно упомянут номер именно счёта, без передачи текста назначения. `amount` — `СуммаДокумента` в соответствующей валюте, `deleted` и `posted` — `DeletionMark` и `Posted`, `paid` — `Оплачено` для поручения и `null` для остальных. Банковские счета, выписки и полные документы в адаптер не передавай.
- Отчёт `scanned` содержит найденные связи, признаки проведения и оплаты в 1С, конфликты реквизитов и однотипные документы с совпавшей суммой. Поручение, расход и заявку показывай отдельно. Совпадение суммы без связи идёт отдельным списком на проверку. Сопоставь документы с текущим этапом оплаты, назначением, датами и распределением по заказам. Для частичной оплаты нужен отдельно подтверждённый остаток. Исполнение в банке проверяется по выписке в обычном порядке навыка.
- Вызови `review` по квитанции запуска `payments`. Для `confirmed` добавь `payment_snapshot` к `invoice_source` и `order_source`. Для живого снимка также требуется `live_payment_readback` после независимой проверки границ выборки и перечитывания найденных документов. При расхождении доступны коды `payment_link`, `payment_status` и `possible_duplicate`. В блоке «Работа Колоса» покажи результат и вердикт этого шага отдельно от сверки строк. Пустая выборка описывает снимок и его границы. Квитанция и вердикт служат для сверки, разрешения на создание, проведение и отправку берутся из штатного навыка.

## Версии памяти

Профиль `.local-data/skill-memory/supplier-invoice/active.json` указывает на версию и SHA-256 неизменяемого `memory.json` в одноимённой подпапке. При обычном запуске память только читается. Отчёты и реквизиты счёта не участвуют в автоматическом обучении. Для новой версии собери обезличенный пример, добавь отдельный контрольный сценарий, сравни обе версии и только после проверки обнови указатель. Для отката верни прежний указатель. Общие с другими навыками процедуры и формат отчёта можно переиспользовать отдельно от памяти счетов.
