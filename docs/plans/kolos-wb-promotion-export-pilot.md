# План пилота Колоса на выгрузках акций WB

Статус — план GStack Autoplan утверждён, локальный пилот реализован. [Утверждённый дизайн](../designs/kolos-wb-promotion-export-pilot.md) · [Инструкция для запуска](../AUTOMATION_SHADOW.md)

Один локальный пилот на Windows. Колос один раз получает от Codex правило учебной версии проверки. Новый процесс проверяет свежий манифест по сохранённому правилу при нуле вызовов модели. Прямой Codex проверяет те же четыре манифеста. Учёт включает все доступные токены за урок и полный цикл.

## Результат пилота

Живой замер 27 ноября 2026 года выполнен на `gpt-6.2-sol` в Codex CLI `0.171.0-alpha.13.2`. Обе ветки дали эталонные ответы на всех четырёх синтетических манифестах. Правило версии v2 требует ровно две свежие выгрузки на акцию. Колос получил его одним вызовом Codex на B и применил на новом манифесте C в другом Python-процессе. Отпечатки загруженных правила и снимка совпали с сохранёнными после урока.

| Манифест | Колос, токены | Прямой Codex, токены |
|---|---:|---:|
| A. Исходная проверка | 0 | 21 367 |
| B. Урок | 21 041 | 21 292 |
| C. Повтор после перезапуска | 0 | 21 684 |
| D. Проверка исходного правила | 0 | 21 380 |
| **Весь цикл** | **21 041** | **85 723** |

Весь цикл с уроком сэкономил 64 682 токена, или 75,45%. Для пары B+C расход составил 21 041 против 42 976 токенов, экономия 51,04%. Суммы включают входные и выходные токены из `usage`. В этом прогоне кэшированный вход равен нулю. Локальная демонстрация с тестовым уроком завершилась за 0,90 с на машине испытания.

Каждый живой прогон сохраняет отчёт локально в `.local-data/wb-promotion-pilot/run-*/report.json`. [Команды для повторения](../AUTOMATION_SHADOW.md#локальный-пилот-на-выгрузках-акций-wb)

## Переход на Kolos-Community

Пилот подготовлен в ветке `codex/wb-promotion-coverage-pilot` от `main`. Перед публикацией база обновлена до [`5820005`](https://github.com/ks-spb/Kolos-Community/commit/58200053c3a91bfeb7969cc2d1bad6c6abcbe696). Этот коммит меняет README.

В новом Git-дереве нет `.local-data`. Локальная демонстрация сама готовит тестовый снимок в каталоге серии. Живой замер использует проверенный исходный снимок, оставленный на компьютере владельца. При запуске из нового checkout к нему можно передать явный локальный путь. В Git, артефакты распространения и вход модели рабочая память не включается. Два существующих набора тестов повторно запускаются на целевой ветке перед изменением кода.

## Продуктовое ревью

Режим — выборочное расширение. Оставляем локальную проверку из согласованного варианта А. Добавляем контрольные прогоны, которые позволяют проверить происхождение правила и достоверность расхода, без новых интеграций.

### Предпосылки

- **Один урок даёт повторяемый результат.** Подходит как проверяемая гипотеза. Codex преобразует текст в условие существующей грамматики. Свежесть, ожидаемые ID и диагностику уже задаёт адаптер. Пилот подтверждает перенос конкретного условия на новый вход.
- **Существующая память нужна при повторе.** Совпадение отпечатков показывает происхождение, а контроль с чужим снимком показывает зависимость от подтверждения правила. В текущем `exceptions` метка подтверждения зависит от операции, поэтому для пилота нужна привязка к содержимому правила и версии.
- **Расход можно сравнить.** Четыре прямых прогона Codex дают выбранную контрольную группу. Исходная версия Колоса готова на старте. Отдельно покажем выводы для пары «урок новой версии и повтор». Сравнение ограничено тестовыми входами и зафиксированным режимом запуска.
- **Есть причина выполнить пилот сейчас.** Действующая автоматизация сначала запускает чат. Без пилота нельзя проверить, окупится ли перенос запуска перед моделью. Ручная настройка порога той же грамматики уже даёт ноль токенов. Ценность урока измеряется возможностью изменить правило короткой инструкцией и проверить его сохранение.

### Альтернативы и горизонт

| Подход | Усилие / риск | Достоинства | Ограничения |
|---|---|---|---|

| Б. Сразу упаковать и подключить | L / высокий | Проверяет установку и весь пользовательский путь. Использует тот же исполнитель | Добавляет права, расписание и установку к первому эксперименту |
| В. Ручное правило | S / низкий | Проверяет нижнюю границу расхода. Использует уже доступное сравнение с порогом | Пропускает преобразование инструкции Codex в проверяемый урок |

```text
Сейчас                     Этот план                    Цель через 12 месяцев
Чат передаёт готовый вход -> Урок, проверка и повтор  -> Колос получает вход сам
Модель стартует первой       на новых данных в CLI       и вызывает модель при исключении
```

Разница с долгосрочной целью — источники, установка и применение на реальных правилах. Урок с одним порогом сам по себе даёт слабую продуктовую дифференциацию. Перед распространением стоит проверить на одном обезличенном рабочем примере, как источник различает файлы и повторы, и сколько работы требует второй вид изменения. Репозиторий Sandy подтверждает наличие прямого воспроизведения сценариев, AgentRun описывает запуск сохранённой процедуры до агента. [Sandy](https://github.com/Sangkwun/sandy) · [AgentRun workflow-first](https://github.com/Parcha-ai/agentrun/blob/main/packages/serve/src/runner/workflow-first.ts)

### Выборочное расширение и порядок работы

1. Начало. Зафиксировать входы, эталоны, чистый каталог, ожидаемые поля и часы МСК.
2. Исполнитель. Разделить факты о свежих и всех попытках, проверить выбор версии и привязку правила к памяти.
3. Подключение. Проверить доступность CLI, изоляцию входов, завершение по таймауту и извлечение токенов из частичного вывода.
4. Приёмка. Повторить запуск новым процессом, сверить отпечатки, выполнить регрессию и оформить сравнение.

Добавлены пять улучшений внутри пилота. Видимые фазы в квитанции, отдельный итог новой версии, контроль другим порогом, подмена снимка при верном правиле и проверка запуска без расходования токенов. Следующие этапы — установочный архив с плагином и расписанием, затем проверка другого рабочего правила. Ручной порог рассмотрен как пояснение контрольной группы. План требует одного нового командного входа и опирается на существующие функции и хранилище.

### 1. Архитектура

Граница пилота проходит по локальному командному входу и отдельному каталогу. В штатной автоматизации расчёт зовётся из `automation_shadow`, а в пилоте вызывается тем же локальным исполнителем из отдельной команды. Один источник правды для новой версии — опубликованный пакет правила и памяти с двумя отпечатками.

```text
До: задача Codex -> automation_shadow -> расчёт WB -> готовый снимок
Пилот: CLI -> расчёт WB -> проверенный снимок -> квитанция
                    \-> только неизвестная учебная версия -> Codex -> локальная проверка
                                                                       \-> снимок и квитанция
```

Состояния версии — отсутствует, проверяется, опубликована, повреждена. Чтение доступно только опубликованной проверенной версии. Откат пилота — новый каталог из исходной копии и сохранение неудачного отчёта. На десятикратном числе строк первым растёт время разбора и сортировки. Внешний Codex ограничивает первые уроки, сохранённый путь от него не зависит.

### 2. Ошибки и восстановление

| Участок | Отказ / класс | Действие | Что видно |
|---|---|---|---|
| Чтение манифеста | отсутствует, `OSError`, `JSONDecodeError`, превышен лимит | завершить до вызова модели | причина и путь к тестовым данным |
| Проверка входа | несовпадение ID, неверное время или тип, `ValueError` / `TypeError` | вернуть ошибку входа | поле и ожидаемый тип или правило |
| Поиск версии | отсутствует / повреждена | для допустимой новой версии предложить урок, при повреждении остановиться | `lesson_required` или ошибка целостности |
| Запуск Codex | бинарник недоступен, отказ доступа, лимит, `TimeoutExpired`, ненулевой выход | один запуск, прочитать доступный JSONL и завершить | категория сбоя, токены либо неизвестный расход |
| Ответ агента | отказ, пустой, повреждённый или не по схеме, использование инструмента | локально отклонить, сохранить доступный расход | причина отклонения, отсутствие опубликованной версии |
| Проверка правила | расходится с эталоном | завершить с ошибкой урока | какая проверка не сошлась |
| Сохранение | конфликт, `AtomicReplaceBlocked`, частичная запись | сохранить только проверенные завершённые версии, прежнюю оставить доступной | куда записать новый прогон или где посмотреть неудачу |
| Сводка | отсутствует часть `usage` либо результат пары расходится | показать известные данные и исход каждой ветки | неопределённый итог или несопоставимые результаты |

Итог каждой ошибки фиксируется прямо в отчёте. Таймаут и ошибка ответа получают разные причины. `usage` извлекается до оценки успешности ответа, поэтому уже израсходованные токены сохраняются, если клиент их успел вернуть.

### 3. Права и данные

Командный вход принимает только подготовленные обезличенные данные. Поля версии, операции и порога проходят строгую проверку. Результат Codex интерпретируется как данные. Проверенные операции исполняются существующей грамматикой по допустимым параметрам.

| Угроза | Вероятность / ущерб | Решение |
|---|---|---|
| Текст из манифеста меняет инструкцию | Средняя / высокий | Передавать только нужные типизированные поля и отдельную инструкцию владельца |
| Внешний запуск видит эталоны, конфигурацию или лишние файлы | Средняя / высокий | Свежий изолированный запуск с выключенными инструментами, проверка журнала событий и состава входа |
| Повреждённое правило подставлено под известную версию | Средняя / высокий | Сверить версию, идентификатор правила и отпечатки пакета до исполнения |
| Каталог запуска указывает на рабочую память | Низкая / высокий | Ограничить запись выделенным каталогом пилота и проверять разрешённый путь |

Учётные данные остаются у установленного клиента. Сырые журналы внешнего CLI не входят в итоговый отчёт. Новых сетевых входов, ролей и зависимостей в этом пилоте нет.

### 4. Потоки данных и граничные случаи

```text
файл -> проверка -> факты/версия -> результат или урок -> сохранение -> отчёт
  |         |            |                   |               |           |
missing   bad/empty   known v1/v2       отказ/таймаут     конфликт     unknown usage
  |         |            |                   |               |           |
ошибка   empty valid   без модели          stop           fail       отчёт NA
```

Пустой валидный календарь возвращает пустые списки. Ожидаемая акция без записей даёт недостачу. Просроченная и неудачная строки сохраняют отдельные признаки. Повторение входа под новым ID запуска проверяет реальное исполнение. Повтор с тем же каталогом и другим входом должен завершиться явным конфликтом.

### 5. Качество кода

Факты манифеста извлекаются один раз и переиспользуются в обеих версиях. Разница между v1 и учебной версией сведена к классификации и отдельному правилу подсчёта излишков. Из бенчмарка заимствуется контракт запуска и разбора JSONL. Его цикл до восьми попыток для пилота не подходит.

### 6. Проверки

Проверяем вход, разбор `usage`, валидацию и обучение на отдельных тестах, затем связываем их прогоном в новом процессе. Синтетический неверный кандидат должен пройти схему и подходящий учебный пример, но провалить закрытую проверку. Живой замер следует после локальных тестов и проверяет две ветки на одном наборе. Ожидаемые результаты и контрольные манифесты остаются у судьи.

```text
Вход и нормализация [unit] -> версия и память [integration] -> новый процесс [E2E]
          CLI/ошибка/usage [unit] -> сравнение с эталоном [integration] -> живой A/B [eval]
```

### 7. Время и нагрузка

Один проход по каждой группе строк и сортировка ID. По входу действует лимит существующего IPC. Отчёт фиксирует полную длительность серии и длительность каждого вызова Codex.

### 8. Диагностика

Квитанция связывает идентификаторы серии и запуска, версию, вход, правило и снимок по отпечаткам. Пользователь сразу видит урок, повтор или ошибку, а также расход. Для воспроизведения нужны тестовый манифест, контрольное время и версия программы. Локальный отчёт покрывает этот сценарий без отдельного интерфейса.

### 9. Запуск и откат

```text
подготовка -> локальные тесты -> один изолированный замер -> сверка артефактов
ошибка -> сохранить квитанции -> новая копия исходного снимка -> чистая серия
```

Пилот выполняется отдельно от рабочего расписания. Изменения штатной базы, поставки и миграции в нем отсутствуют. Первая проверка после реализации проходит с тестовым ответом Codex и двумя процессами. Затем можно провести измерение в одобренной среде Windows.

### 10. Траектория и отложенные задачи

Обратимость 5/5 для локальной серии. Самая вероятная долгосрочная ошибка — размножить отдельные ветки под каждое новое правило. Две учебные версии проверяют стабильную границу между извлечением фактов и правилом. Подключение реального источника, планировщик, публичный пакет, новые типы правил и второй провайдер отложены до доказательства на этом стыке.

## Ревью запуска из командной строки

Режим — DX Polish. Первый пользователь — владелец рабочего checkout на Windows. У него установлены Python и Codex. Ему важно получить первый результат до расхода токенов, затем осознанно запустить сравнение. Будущие команды из корня репозитория:

```powershell
py -3 -B -m kolos_states.wb_promotion_pilot local
py -3 -B -m kolos_states.wb_promotion_pilot compare --model <поддерживаемая-модель> --base-snapshot <локальный-путь-к-снимку>
```

Команда `local` создаёт серию в `tests/desktop-output/wb-promotion-pilot/`. Команда `compare` хранит серию со снимком в `.local-data/wb-promotion-pilot/`, вне артефактов CI. `--base-snapshot` указывает на локальный `memory.json` исходного графа. ### Архитектура и контракт

```text
Windows CLI
|-- local   -> тестовый исходный снимок и контролируемый ответ
|-- compare -> копия исходной памяти + проверка среды -> Codex CLI
`-> валидатор манифеста + фиксированный момент МСК -> общие факты WB
       |-- исходная версия  -> текущее правило и текущая диагностика
       |-- учебная версия  -> проверенный рецепт и подтверждение в памяти
       `-- урок            -> запись попытки -> JSON-ответ -> локальный судья
                                 |                              |
                                 +--- сохранённый usage        `-> комплект и метка публикации
                                                                          |
новый процесс, адаптер отключён -> читает и проверяет комплект -----------+
                                                     |
                                                     `-> результат и квитанция -> сводка A/B
```

Кандидат содержит активную учебную версию, фиксированный вид операции «ровно N свежих выгрузок» и целый положительный `N`. Схема отклоняет лишние поля. Локальная проверка отклоняет `bool`, строки, ноль, отрицательные значения, неизвестное имя операции и чужую версию. Обработка штатного v1 использует существующие признаки. В учебной версии `count < N` даёт недостачу, `count == N` — полноту, `count > N` — излишек. Границы берутся из принятого рецепта и контрактного формата. Для учебных манифестов одна свежая строка означает один отдельный файл.

Изоляция и права. `compare` до запуска проверяет доступность указанного клиента, поддержку нужного профиля ограничений и наличие границ безопасного рабочего каталога. В ветке Колоса вызов доступен только на явном шаге урока с валидной учебной версией и отсутствующим опубликованным пакетом. Прямая ветка запускает Codex отдельно для каждого контрольного манифеста. Неподдерживаемая версия, повреждённый или прерванный урок дают понятный отказ до вызова. Передаётся только проекция разрешённых полей тестового входа, версия, инструкция и схема. Пути, сырые сообщения источника, эталоны и память остаются у локального процесса. Инструменты и коннекторы отключены. Границу проверяем до отправки данных и по событиям выполнения. Если подтвердить ограничения на Windows не удаётся, живой запуск недоступен. [Настройки Codex](https://learn.chatgpt.com/docs/config-file/config-basic#feature-flags)

### Состояние урока и сохранение

```text
отсутствует -> попытка зарезервирована -> ответ получен -> проверен -> опубликован
                   |                       |                |
                   `------ прерван --------+--- отклонён ---+
Опубликован -> проверка целостности при чтении -> исполняется или ошибка
```

Для одной серии и версии резервируется одна попытка до внешнего запуска. Запись резерва сохраняется при аварии и позволяет объяснить, что исход неизвестен. Квитанция сохраняет состояние попытки и доступный `usage` до валидации кандидата. После проверки снимок и правило записываются в отдельный каталог, перечитываются, затем публикуется атомарная метка с версией и обоими отпечатками. Читатель открывает версию после публикации этой метки. [Хранилище](../../kolos_states/storage.py) · [Атомарная запись](../../kolos_states/ipc.py)

В граф памяти записывается подтверждение конкретной версии и отпечатка правила. Проверка при загрузке учитывает оба файла и наличие этого подтверждения. Подмена исходным снимком с той же операцией даёт отказ, даже если описание правила сохранилось. Исходная память читается через проверяемый `restore_snapshot`, поскольку `Store.load` умеет мигрировать и записывать данные. Резерв и следы стадии публикации остаются в серии. Откат — открыть новую серию и взять исходную копию.

### Качество кода и диагностика

Факты манифеста разбираются общей функцией, затем v1 и учебное правило строят свой результат. Пилотная проверка типа и размера входа выполняется до общего разбора. Из схемы и грамматики принимаются только разрешённые значения, поскольку `render` формирует исходный текст из переданных параметров. Функции расчёта не зависят от клиента Codex. Код опирается на штатные JSON, проверку графа и следующий порядок публикации. Вводить общий движок плагинов для двух режимов не требуется.

Каждый вызов Codex строится массивом аргументов и получает только данные по stdin. Фиксируются одинаковые версия клиента, модель и настройки для урока и прямых прогонов. Разбор полных событий JSONL идёт до проверки результата и учитывает часть stdout при таймауте. Конфликтующие повторные события, неизвестные поля расхода и отсутствие итогового события дают неизвестный итог при сохранении достоверной части. Кэшированный вход входит во входные токены. Проверка схемы финального ответа отделена от проверки `usage`. [Формат событий Codex](https://learn.chatgpt.com/docs/non-interactive-mode#make-output-machine-readable) · [Таймаут дочернего процесса](https://docs.python.org/3/library/subprocess.html#subprocess.TimeoutExpired)

Квитанция имеет версию схемы, ID серии и запуска, этап, версию правила, зафиксированное время, хеши входа, правила и памяти, источник снимка, результат и код ошибки. Отдельно записываются способ определения результата, число запусков внешнего процесса, фактические токены, полнота учёта, модель, версия клиента и длительность. Пропущенный шаг, отсутствие вызова и неизвестный расход различимы. Успешная серия сравнивает четыре пары по одному эталону. Для ошибки сохраняем пройденные этапы, известный расход и причину завершения.

### Время, ресурсы и исполнение

Запись и чтение снимка ограничены текущими 4 МБ. Для входа применяется существующий предел IPC. Общий разбор считает строки один раз и сортирует наборы ID. Для урока действует предельное время вызова Codex. При повторном запуске Колос читает сохранённое правило и проверяет новый вход. В отчёте указана длительность серии и каждого модельного вызова.

Реализация идёт последовательно по одному модулю. Сначала договорённость об эталоне и изолированное чтение. Затем рецепт, хранилище и переходы. После них локальная команда и проверки перезапуска, далее модельный запуск и отчёт. Эта последовательность исключает параллельную правку одних и тех же контрактов.
