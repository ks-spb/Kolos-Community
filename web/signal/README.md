# Kolos: распространение сигнала (v1)

База: `feature/browser-graph-lab` @ `8f8e166e50cfe216827e75505378be177f55dabf`.
Старый `src/engine.ts` и desktop-файлы не изменяются. Второй движок находится
в `signal/core.mjs`, интерфейс — `signal/ui.mjs`. Это проверяемая инженерная
модель с контекстом и конкуренцией, не утверждение о биологическом сходстве мозга.

## Запуск

`npm ci && npm test` собирает оба режима в один `dist/index.html`.
Готовый HTML открывается без установки и не делает внешних запросов.
`npm run dev` запускает локальную страницу. Оба режима доступны через переключатель
сверху. Переход между режимами ставит прежний движок на паузу; запись обучения
сначала требуется сохранить/сбросить. Память режимов независима.

Первая проверка:

1. Выбрать «Распространение сигнала», «Пример CALC → 1700».
2. «Передать запрос» — он распознаётся посимвольно до явной границы запроса.
3. «Продолжить по сигналу» — MOVE → CHECK → CLICK → KEY 1 → KEY 7 → KEY 0 → KEY 0 → конец.
4. «Новая попытка», переставить или скрыть CALC, затем повторить шаги 2–3.
5. При перемещении должны выполняться отдельные узлы поиска и повторной проверки;
   при исчезновении — остановка до клика. «Показать все» + продолжение возобновляет попытку.

Собственное обучение: написать запрос → начать запись → кликнуть объект → ввести
клавиши в поле демонстрации → Escape → сохранить → «Правильно». Два одинаковых
запроса с разными демонстрациями могут дать неоднозначность: это наблюдаемый результат,
а не повод выбирать по ID. Вес входящей стрелки редактируется в правой панели.

## Продолжить по памяти

Это отдельный режим от полного выполнения команды.

- «Передать запрос» добавляет после введённого текста обязательный контекст конца запроса и затем допускает переход к ACTION-вершинам.
- «Продолжить по памяти» сначала точно распознаёт введённый префикс, но **не** подаёт END после него. После последнего введённого символа все допустимые следующие input-контексты конкурируют по обычной формуле активации.
- Каждый сгенерированный символ выбирается отдельным логическим тактом. Готовая сохранённая строка не режется и не возвращается как суффикс.
- Победивший символ становится новым подтверждённым контекстом и посылает следующий импульс.
- Автодополнение заканчивается, когда по сигналу выигрывает контекст `<END_REQUEST>`. END не показывается пользователю и не запускает ACTION-цепочку.
- Один первый пробел сгенерированного хвоста остаётся в графе и журнале как `␣`, но скрывается в отображаемом ответе. Поэтому `добавь траты` → внутренне `␣1700` → пользователю `1700`; `добавь` → внутренне `␣траты 1700` → `траты 1700`.
- Если лучший сигнал ниже порога, продолжение останавливается. Если два кандидата отличаются меньше `margin`, результат — «Неоднозначное продолжение»; технический ID не используется как tie-break.
- Максимум 200 автоматически созданных символов; повтор того же контекстного узла останавливает генерацию как цикл.
- Явная положительная/отрицательная оценка после автодополнения применяется только к связям **сгенерированного хвоста**. Введённый пользователем префикс не получает награду за то, что уже был известен.
- Регистр и пробелы в первой версии значимы: префикс должен точно совпасть с началом хотя бы одной обученной цепочки.

Пример для обученного `добавь траты 1700`:

```
добавь траты
  -> ␣ -> 1 -> 7 -> 0 -> 0 -> END
  -> ответ: 1700

добавь
  -> ␣ -> т -> р -> а -> т -> ы -> ␣ -> 1 -> 7 -> 0 -> 0 -> END
  -> ответ: траты 1700
```

## Модель

- Узел контекста создаётся/переиспользуется по предыдущему контексту, типу события
  и содержимому. Общие понятия хранятся отдельно. Поэтому два нуля в 1700 — разные
  контекстные узлы одного KEY 0. Refractory на них независим.
- `active` — подтверждённый текущий контекст, не индекс следующего действия.
- `pulses` — события срабатывания прошлого такта. Только они возбуждают соседей.
- Входящий символ — внешний обязательный признак при распознавании. Узел конца
  запроса не допускает раннее исполнение незавершённой команды.
- ID используется только для адресации/отображения. Нет `ID+1`, чтения `pyt`, списка
  будущих действий или выбора следующего пункта массива демонстрации при исполнении.
  Демонстрация используется только при построении графа.
- `excite` / `inhibit` передают взвешенный импульс; `requires` показывает обязательные
  условия среды; `denotes` связывает контекст с понятием/действием. Требования также
  проверяются независимым неизменяемым guard. Произвольное ослабление веса не отменяет guard.
- У видимого объекта нет разрешения самостоятельно кликнуть. Кандидат должен быть
  привязан к текущему контексту, фазе и входу, пройти guard и refractory.

Такт синхронный: все величины считаются по одному снимку, не по порядку массива.

```
A' = clip(decay*A + sum(P*w*spike) + context + observation - inhibition, 0, 1)
context = min(contextGain, sum(contextGain*w*trace_source))  # только для новых импульсов
```

Наблюдение добавляется один раз при новой версии среды, не на каждом кадре.
В обычном графе после одного подтверждённого шага срабатывает один источник;
несколько реально поданных источников также суммируются (проверено тестом).
После расчёта выбирается максимальная допустимая активация выше индивидуального
или общего порога. Равенство либо недостаточный отрыв → остановка. Технический ID
не разрешает равенство. Затухание без новых событий не создаёт новую причину действовать.

После подтверждения: A=0, trace=1, refractory=2 (по умолчанию); создаётся новый
импульс P=1. Поэтому длинная цепочка не затухает как последовательное умножение
одного и того же сигнала. Проигравшие подавляются, а потенциалы вне текущего
контекста обнуляются на следующем такте. Refractory — две следующие возможности
срабатывания, а не два браузерных кадра. Есть общий предел 600 тактов попытки.

«Продолжить» после блокировки/изменения весов — явная операция `wake`: очищает старые
неоднозначные потенциалы и повторяет импульс из подтверждённого контекста.
Это не непрерывная подпитка сети одним и тем же входом.

## Действия и проверка среды

`preview` вычисляет следующий такт на копии состояния, включая предполагаемый
эффект в виртуальной среде. До конца анимации эти данные помечены как расчёт,
а память и среда не меняются. На commit проверяются ревизии ядра и среды.
Модель и эффект применяются синхронно; повторный commit отклоняется.

MOVE использует старые координаты. CHECK либо подтверждает объект под курсором,
либо открывает в графе ветку `seek → recheck`. CLICK требует актуальной успешной
проверки и правильного объекта непосредственно перед фиксацией. KEY требует фокус
ожидаемого приложения, сохранённого при демонстрации. Исчезновение объекта не
вызывает негативного обучения. Если объект снова доступен, нужна явная команда продолжить.

Это виртуальная среда, не вычисления настоящего калькулятора и не запись финансов.
Обработка неоднозначных/пропавших объектов прекращает цепочку без случайного клика.

## Обучение весов

Новая связь .85; повторные демонстрации не размножают источники тока. `eligibility`
помечает только реально использованные связи, затухает .99 за такт. Награда
обновляет `w += rate * reward * eligibility` с ограничением 0–1. По умолчанию
+0.05 за положительную оценку, -0.10 за отрицательную. Негативная оценка штрафует
последнее действие, а не узел ожидаемого конца. Повторная оценка без новых
выполненных связей отклоняется. Сам конец цепочки не даёт награды.

Настройки сети, вес каждой стрелки, индивидуальный порог и тормозящие связи доступны
в интерфейсе. Скорость анимации не входит в конфигурацию двигателя.

## Хранение и повтор

Отдельная IndexedDB `KolosSignalLab` и блокировка вкладок `kolos-signal-autosave`.
Вторая вкладка может экспортировать свой опыт, но не перезаписывает автосохранение
первой. Ошибки хранилища видны; JSON остаётся резервным способом сохранения.
При перезагрузке движок всегда на паузе. Частичный preview не считается исполненным.

JSON `kolos-signal-ui/1` содержит `kolos-signal/1` — версионированный журнал операций:
обучение, ввод, такты, среда, веса и параметры, оценки. Снимки каждого шага восстанавливаются
детерминированно на копии, без действий в живой среде. Незавершённая демонстрация
сохраняется как остановленный черновик. Ползунок/повтор истории не обучают сеть.

«Из последовательного» копирует только явно записанные ACTION-демонстрации с
положительной оценкой. Текстовые эпизоды без ясной границы демонстрации не угадываются.
Оригинальная память не меняется. Сигнальные JSON не загружаются в старый двигатель.

Ограничения: 1000 узлов, 2000 операций эксперимента, 200 символов запроса,
100 действий демонстрации, 24 объекта, файл до 12 МБ. Нет автоматической подстановки
2500 вместо обученных 1700; нет LLM, перефразирования запросов, настоящего Glaz и
мыши ОС. Встроенный recovery-подграф — явно заданная инженерная опора, а не
самостоятельно открытое сетью поведение.

## Проверка

`node --test tests/signal.test.mjs` — отдельные проверки:
повторные нули, перенумерация ID, перестановка массивов, сумма источников, веса,
торможение, пороги, refractory, неоднозначность, отсутствие входа, позиций/объектов,
ревизии preview, idempotency, обучение/оценки, история и импорт.

`python tests/signal_browser.py` — оба режима в одном HTML, пауза, один такт,
1700, moved/hidden CALC, собственное обучение 2300, JSON, IDB и мобильный экран.
`KOLOS_INLINE_TEST=1` использует set_content при запрете локальной навигации и
НЕ заявляет проверку IndexedDB reload или физической загрузки JSON. HTTP-режим
на GitHub runner проверяет это отдельно.
